# 概要
`implementation` は設計に基づいて実装を進める Skill である。  
原則は「`docs/tasks.md` の未完了先頭タスクのみ実装する」。タスク粒度を超える実装は避ける。

# このSkillを使う場面
- `docs/tasks.md` にある未完了タスクを実装するとき
- 既存要件・設計が揃っており、実装に着手できるとき
- 小さく安全に変更して進捗を積み上げるとき

# このSkillを使わない場面
- 先に要件や設計の見直しが必要なとき
- 大規模な仕様変更の合意前で、前提が不安定なとき
- テスト追加のみが目的のとき（`test` を使う）

# 入力
- ユーザー依頼
- `AGENTS.md`
- `docs/requirements.md`
- `docs/design.md`
- `docs/tasks.md`（未完了先頭タスクを特定するため必須）
- 画面実装時は `.codex/skills/implementation/ui-concept.md`（必読）
- 画面実装時は `.codex/skills/implementation/ui-style-guide.md`（必読）
- 既存コードベース

# 出力
- 未完了先頭タスクに対応する最小限のコード変更
- 必要に応じた `docs/tasks.md` のステータス更新（`TODO/DOING/DONE/BLOCKED`）
- 実施した確認手順と結果、次に進むべきタスクの提示
- 実装完了後の説明（Go初学者にも分かる平易な説明 + レビュイー視点の実装意図と判断理由）

# 画面実装ルール
- 画面実装は Tailwind CSS + CSS Module を基本構成とする
- 余白・レイアウト調整は Tailwind CSS を優先して利用する
- `global.css` は最低限（リセット/フォント/共通import）にとどめる
- Tailwind で表現しきれない箇所だけ CSS Module を追加する
- 画面実装前に `.codex/skills/implementation/ui-concept.md` を必ず読み、記載コンセプトを維持する
- 画面実装前に `.codex/skills/implementation/ui-style-guide.md` を必ず読み、余白/タイポ/サイズの統一ルールを適用する
- API/BATCH/DOCS など画面実装を含まないタスクでは `ui-style-guide.md` を読まない

# 作業手順
1. `AGENTS.md` と `docs/requirements.md` / `docs/design.md` を確認し、実装前提を揃える。
2. 画面実装を含む場合は `.codex/skills/implementation/ui-concept.md` と `.codex/skills/implementation/ui-style-guide.md` を必ず読み、デザイン方針と実装ルールを確認する。
3. 画面実装を含まない場合は UI 文書を読み込まず、対象レイヤーの実装に集中する。
4. `docs/tasks.md` から未完了先頭タスクを1つ特定する（原則この1件のみ対応）。
5. 影響範囲が大きい場合は、変更内容・前提・影響を先に説明する。
6. タスク達成に必要な最小限のコード変更を行う。コードの意図が伝わりにくい箇所には、日本語コメントを適度に記述する。関数には「その関数が何をするか」が分かる説明コメントを原則として付ける。特にミドルウェア、境界条件、認可・業務ルールの分岐では「なぜ必要か」「何を守っているか」が伝わるコメントを省略しない。
7. 変更に対する最小限の確認（ビルド、実行、関連チェック）を行う。
8. `docs/tasks.md` のステータスを更新し、結果と次タスクを報告する。
9. 実装完了報告では、以下を必ず含める。
   - Go初学者向けに「何を変更したか」「処理の流れ」を平易に説明する
   - レビュイーの立場で「なぜこの実装にしたか（代替案との差分、採用理由、守っている要件/制約）」を説明する
   - 説明は要点に絞り、箇条書きで示す
   - 各要点には対応するソースコード（ファイルパス + 主要箇所）を必ず添える
   - 冗長な文章を避け、1項目ごとに「実装内容」と「意図」が対応して読める構成にする

# 禁止事項
- 未完了先頭以外のタスクへ無断で着手しない
- 要件や設計の未確定事項を実装で勝手に固定しない
- 一度に広範囲のリファクタや無関係変更を混ぜない
- 意図が読み取りにくい実装を、コメント補足なしで残さない
- 関数の役割がコメントなしで分からない状態を残さない
- 確認手順なしで完了扱いにしない

# 完了条件
- 未完了先頭タスク1件が実装され、目的が達成されている
- 実装内容が要件・設計と矛盾しない
- 確認手順と結果、次に進むべきタスクが明示されている
- 実装意図の説明が、Go初学者にも追える粒度で提示されている

# コミットメッセージ規約
- 形式は `T-xxx: 変更内容` に統一する（例: `T-013: Add admin user status update API`）
- `T-xxx` は対応タスクIDを必ず先頭に付ける
- 変更内容は英語の命令形で簡潔に記述する（`Add`, `Update`, `Fix`, `Refactor`, `Docs` など）
- 1コミット1目的を前提に、説明は1行で読める粒度に保つ
