# 概要
`requirements` は「何を満たすべきか」を定義・更新するための Skill である。  
成果物は主に `docs/requirements.md` とし、必要に応じて `docs/tasks.md` の要件対応関係を整える。

# このSkillを使う場面
- 新機能や運用ルールの要件を追加するとき
- 既存要件の曖昧さ・矛盾を解消するとき
- 受け入れ基準（CA）や前提・制約（AC）を見直すとき
- 実装前にスコープ確定が必要なとき

# このSkillを使わない場面
- 実装方式やAPI/DB構造など「どう作るか」を決めるとき
- 既存設計に従ってコードだけを変更するとき
- テストケース追加や実行手順整備のみを行うとき

# 入力
- ユーザー要求、背景、制約
- `AGENTS.md`
- `docs/requirements.md`
- 必要に応じて `docs/design.md` と `docs/tasks.md`

# 出力
- 更新された `docs/requirements.md`（必要箇所のみ）
- 必要時の `docs/tasks.md` への要件対応追記
- 変更要点（追加・変更・保留）と確認観点の簡潔な報告

# 作業手順
1. `AGENTS.md` を読み、文書運用ルールと表現方針を確認する。
2. `docs/requirements.md` を読み、既存要件ID（FR/NFR/OPS/AC/CA）との整合を確認する。
3. 変更対象を「追加・修正・保留」に分け、要件として必要最小限で記述する。
4. 要件に影響する未確定事項は断定せず、前提・保留点として明記する。
5. 要件変更の影響がある場合のみ `docs/tasks.md` の対応関係を更新する。
6. 変更内容を短く要約し、次に `design` で詰めるべき論点を示す。

# 禁止事項
- 実装詳細（クラス設計、具体API仕様、実行手順）を要件に混在させない
- 根拠なしに既存要件IDを削除・再採番しない
- 未確定事項を確定事項として断定しない
- コード実装やテスト実装をこの Skill の主目的として進めない

# 完了条件
- 要件変更が `docs/requirements.md` に反映され、既存要件と矛盾しない
- 変更の意図と影響範囲が読んで分かる
- 次フェーズ（`design`）で検討すべき点が明示されている
