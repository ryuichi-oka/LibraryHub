# 概要
`design` は「どう作るか」を定義・更新するための Skill である。  
成果物は主に `docs/design.md` とし、必要に応じて `docs/tasks.md` に設計起点のタスクを反映する。

# このSkillを使う場面
- 要件を実装可能な設計に分解するとき
- API、データモデル、画面構成、業務ルールの整合を取るとき
- 要件変更に追随して設計を更新するとき
- 実装前にトレーサビリティを明確にしたいとき

# このSkillを使わない場面
- 要件IDの新設や受け入れ基準の再定義が主目的のとき
- コードを直接変更するとき
- テストコード追加と実行確認だけを行うとき

# 入力
- ユーザー要求、制約
- `AGENTS.md`
- `docs/requirements.md`
- `docs/design.md`
- 必要に応じて `docs/tasks.md`

# 出力
- 更新された `docs/design.md`（必要箇所のみ）
- 必要時の `docs/tasks.md` 更新案（設計起点の実装タスク）
- 設計判断の要点と残課題の簡潔な報告

# 作業手順
1. `AGENTS.md` を確認し、文書ポリシーと進め方ルールに合わせる。
2. `docs/requirements.md` の該当要件IDを確認し、設計対象を特定する。
3. `docs/design.md` の現行構造に沿って、変更点を最小単位で反映する。
4. 要件IDとの対応（トレーサビリティ）を崩さないように記述する。
5. 設計変更が新規実装を生む場合のみ `docs/tasks.md` への反映点を整理する。
6. 実装に渡す前提、未確定事項、リスクを短く明記する。

# 禁止事項
- 要件未確定の内容を独断で確定しない
- 実装コードの細部に踏み込みすぎて設計文書を実装手順書化しない
- 要件IDとの対応を失う変更をしない
- 実装やテスト実行をこの Skill の主目的として進めない

# 完了条件
- `docs/design.md` が要件と整合し、実装可能な粒度になっている
- 主要な設計判断と前提が明記されている
- 次フェーズ（`implementation`）で着手できる状態になっている
